# 外场实验准备与数据需求汇报

版本：V1.0  
日期：2026-09-12  
用途：提交导师审阅，作为后续外场采集、数据集建设和模型实验的准备依据  
文件性质：实验准备提案，不代表设备能力或场地条件已经确认

## 一、请导师先审阅的结论

本项目不建议把外场工作安排成一次性采集，而应分为“设备演练、Pilot、扩展采集、锁定评价”多轮实验。每一轮的目的和数据状态不同，不能混用。

当前最需要确认的不是网络结构，而是以下事实：

1. 雷达能否保存 H/V 两通道原始复数 IQ，以及每个脉冲或扫描的真实顺序；
2. 雷达、视频、目标操作记录和测距/测角真值能否统一到可靠时间轴；
3. H/V 通道的物理含义、同步关系和幅相标定条件是否明确；
4. 合作场地、可用设备、操作人员和安全边界是否允许重复采集；
5. 能否为目标和背景建立同日期、同场地、同配置的对照数据。

在这些事实确认前，本项目保持 `4/6 BLOCKED_EXTERNAL`，不把新数据计划写成已经完成的空飘球识别或实时部署结果。

## 二、实验要回答的问题

### 2.1 本学期主问题

```text
可靠采集链
  -> Power2/RD 单域基线
  -> H/V 与时域/时频等多域融合比较
  -> 气象和场地分层鲁棒性
  -> 因果回放与实时性
  -> 冻结评价和论文/汇报
```

目标任务按难度逐层推进，不跳过前一层：

```text
目标/背景检测
  -> 空飘球/其他目标
  -> 有载/无载
  -> 载荷类别或运动状态
```

当前已有 UAV/背景结果只能作为检测前端和方法开发依据。只有在新数据具备对应对象、标签和真值后，才讨论空飘球载荷识别。

### 2.2 数据需求与研究问题的对应关系

| 研究问题 | 必须具备的数据 | 不能用什么替代 |
|---|---|---|
| 单域与多域是否公平可比 | 同一批 session 的原始 IQ、固定配置、统一 split 和相同训练预算 | 只比较不同日期或不同样本来源的结果 |
| H/V 特征是否有增益 | H/V 通道定义、复数性、相干/同步证据、标定记录 | 文件名、图片或未说明的处理后功率 |
| 时域/时频特征是否可信 | 连续慢时间 IQ、PRF、脉冲序号、真实时间轴 | 用文件 mtime 或 beam/azimuth 顺序猜采集时间 |
| 气象是否影响模型 | 带时间戳的风速、风向、阵风、温湿度等，以及同条件目标/背景 | 只写“晴天/阴天”或用日期代替天气 |
| 场地鲁棒性是否成立 | `site_id`、朝向、遮挡、强反射体、照片/平面图和背景对照 | 把场地名称当成类别标签 |
| 定位和实时性是否成立 | 距离/速度/角度真值、测量误差、硬件时间、运行日志和资源记录 | 只报告网络输出或单次平均耗时 |

## 三、多轮实验安排

一轮实验可跨多个日期；一次连续启动和停止的采集称为一个 `session`。重复实验必须新建 `session_id`，不能覆盖原文件。

| 轮次 | 目的 | 建议内容 | 数据状态 | 允许用途 |
|---|---|---|---|---|
| E0 设备与无球演练 | 确认设备、写盘、同步、视频和备份链路 | 原始 H/V 样例、连续写盘不少于 300 s、可见同步事件、纯背景 | `engineering` / `dry_run` | 接口和质量检查；不产生模型性能结论 |
| E1 Pilot | 验证场景、标签、真值和同条件背景是否可重复 | 四场景各至少 3 个独立 session，每段 2--5 min | `development` | 发现问题、建立初步数据卡和开发集 |
| E2 扩展采集 | 增加日期、场地、天气、对象和运动状态 | 在设备稳定后分批采集，优先保证每个条件有目标/背景对照 | `development` / `validation` | 训练、调参、分层验证和模型比较 |
| E3 锁定评价 | 检查冻结模型在新条件下的表现 | 新日期或新场地，目标和背景同时存在 | `locked_test` | 模型、特征、阈值和后处理冻结后只评价一次 |

E1 若失败，重做 E1；不能把未通过的 Pilot 直接升级为 E2 或 E3。E3 尚未满足条件时，报告中应写“锁定外部评价未执行”。

## 四、必须采集的数据

### 4.1 雷达原始数据和设备配置

每个正式 session 至少应保留：

- H/V 两通道原始复数 IQ；若不能同时保存，应记录交替采样方式、通道时间差和可用范围；
- 雷达型号、序列号（可只存受控目录）、软件/固件版本；
- 中心频率或频段、PRF、带宽、脉冲宽度、每帧脉冲数、距离门和采样率；
- 一帧、波束、扫描、文件和硬件序号之间的关系；
- IQ 的文件格式、变量名、数组维度、数据类型、量化和缩放系数；
- 采集前是否做脉冲积累、检测、门限、降采样、相位校正或其他不可逆处理；
- `radar_config_id`、配置导出文件和对应 SHA-256。

只保存 RD 图片、幅度图或功率图，不能满足原始极化、连续慢时间和后续时频分析的最低要求。

### 4.2 时间、顺序和同步

- 逐脉冲或逐帧 UTC 时间戳，或能与 UTC 对齐的硬件时间；
- 单调且唯一的 `hardware_sequence`，以及 `scan_id`、`frame_id`、`pulse_id`；
- 时钟来源、精度、重置计数、丢帧/缓存溢出记录；
- 雷达、视频、真值记录和气象设备的时间映射；
- 至少 5 次清楚的同步事件，记录事件发生时间和误差；
- 状态标签的开始、结束和不确定区间。

文件名时间、MAT header 时间和文件系统 mtime 不能代替真实采集时间。没有真实顺序时，只能做 `capture` 档数据整理，不能宣称因果历史模型或严格实时。

### 4.3 目标真值与定位

每个目标 session 需要同时记录：

- `target_present`、目标类别和层级标签；
- 球体/载荷配置、运动状态和状态起止时间；
- 距离、速度、方位或角度的测量值及测量方法；
- 目标操作口令、视频时间段、轨迹或位置变化；
- 测距/测角设备型号、精度和校准状态；
- 无法确认的标签标记为“不确定”，不得事后按模型输出修改真值。

第一轮 Pilot 只建议固定一种球体和一种载荷，先比较“无载/有载/运动状态”的可记录性；不要同时改变球体、载荷、距离、悬挂方式和运动方式。

### 4.4 气象数据

建议使用带时间戳的仪器记录，最低包括：

- 风速、风向、阵风；
- 温度、相对湿度、气压；
- 降水和能见度（若现场条件允许）；
- 传感器位置、高度、采样间隔、设备型号和校准信息。

天气在第一阶段作为元数据、分层变量和鲁棒性条件，不强制增加天气分类头。连续测量优先于手工写“晴/阴/雨”；后续可根据样本量再决定如何分箱。

### 4.5 场地和背景

- 唯一 `site_id`、雷达位置和朝向；
- 开阔地、建筑区、树木区等定性类别；
- 遮挡、地面、建筑、金属设施和其他强反射体；
- 现场照片、简图或可公开的平面示意；
- 纯背景 session 及其采集时间；
- 场地授权和安全边界。

每个重要场地、日期和雷达配置都应尽量同时采目标和背景，避免“场地=类别”或“日期=类别”的泄漏。

### 4.6 对象构型

若后续要研究空飘球有载/无载或载荷类型，必须记录：

- 球体型号、尺寸或可用规格；
- 载荷类别、质量、外形和安装方式；
- 绳长、悬挂方式、材料和连接状态；
- 是否摆动、旋转、稳定或受风影响；
- 对象编号和重复使用情况。

对象信息不完整时，只能报告检测前端，不应声称载荷分类结论。

### 4.7 运行、质量和可追溯信息

- `experiment_id`、`session_id`、`radar_config_id`、`calibration_id`；
- 操作人员、设备状态、开始/结束 UTC 和异常说明；
- 文件大小、时长、首末序号、丢帧、饱和和缓存溢出；
- 预处理、推理和后处理版本；
- 处理耗时、CPU/GPU/内存、队列积压和持续运行时长；
- 原始文件、视频和真值的双份备份哈希。

### 4.8 数据记录的五个层级

同一份实验数据需要同时在不同层级记录，不能只保存切片后的训练样本：

| 层级 | 唯一标识 | 必须记录的内容 | 主要用途 |
|---|---|---|---|
| 实验批次 | `experiment_id` | 实验目的、版本、负责人、允许用途、日期范围 | 区分 E0/E1/E2/E3 和不同研究问题 |
| 采集会话 | `session_id` | 一次连续启动/停止、场景、配置、标定、人员、异常 | 分组划分和重复性统计 |
| 扫描/帧 | `scan_id`、`frame_id` | 时间、硬件序号、波束关系、丢帧和状态 | 因果顺序、连续轨迹和事件边界 |
| 目标事件 | `event_id` | 目标出现/消失、状态、真值、视频区间、测量误差 | 事件级检测、定位和虚警率 |
| 模型样本 | `sample_id` | 来源 session/scan/event、窗口范围、标签、派生特征版本 | 训练、验证、测试和结果回溯 |

训练样本可以由扫描切片得到，但必须能通过 `sample_id -> event_id -> scan_id -> session_id -> experiment_id` 回溯到原始文件。随机切片后的样本不能单独作为独立样本计数。

### 4.9 按当前研究任务拆分的数据包

下表是本项目真正需要组织的实验数据包。每个数据包可由多个实验批次组成，但必须保持自己的目的和分组规则。

| 数据包 | 要回答的问题 | 必须包含 | 必须包含的对照 | 主要输出/放行条件 |
|---|---|---|---|---|
| D1 采集链与标定 | 数据是否能被正确读取、排序和解释 | 原始 H/V IQ、配置、PRF、时间/序号、同步事件、标定参考、写盘日志 | 空场/参考目标/重复同步事件 | 通过 capability、synchronization、calibration、dry run 五道门 |
| D2 检测与定位基线 | 新数据上的 Power2/RD 单域能力如何 | 目标与背景、距离/速度/角度真值、观测时长、SNR、连续或可计数事件 | 同日期/场地/配置背景；不同距离和速度层 | Pd、Pfa、Joint Pd、距离/速度/角度误差；先冻结基线再加融合 |
| D3 多域融合 | H/V、时域、时频是否提供可归因增益 | 同一 session 的 Power2、RD、原始/时域窗口、连续慢时间、可验证 H/V 特征 | 同一 split、同一训练预算的单域模型 | 固定阈值规则下报告 Pd/Pfa/Joint Pd、定位、最差组和资源；不能只看 AUC |
| D4 环境与场地鲁棒性 | 模型是否利用日期、天气或场地捷径 | 气象连续记录、site 元数据、背景强度/杂波摘要、目标和背景事件 | 每个日期/场地尽量同时有目标与背景 | 按日期、场地、天气、SNR 分层的性能和混杂检查；外层组隔离 |
| D5 因果与实时性 | 历史上下文和本地运行是否真的可用 | 逐帧真实时间、硬件序号、丢帧/重启、连续流、推理日志、资源和队列 | complete-scan、leave-one-out 仅作诊断；past-only 需真实顺序 | P50/P95/P99 延迟、吞吐、内存、丢帧和持续运行；没有真实顺序不得宣称实时 |
| D6 空飘球分层识别 | 能否从检测前端进一步区分对象和状态 | 空飘球、其他目标、无载/有载、稳定/摆动/旋转、对象构型和同步视频 | 同场地背景、同一球体无载/有载配对、不同对象实例 | 先检测，再球/非球，再有载/无载，最后才考虑载荷类别；标签不足时只保留前一层 |
| D7 物理解释与特征验证 | 模型变化是否与可观察的散射、运动和环境因素一致 | 目标几何/材料、姿态或摆动状态、雷达观测几何、标定参考、同步视频和气象 | 固定参考目标、空场、同对象不同状态的重复测量 | 只报告有数据支撑的相对趋势；无绝对标定时不写绝对 RCS、ZDR 或物理微多普勒 |

数据包之间有先后关系：D1 不通过，D3/D5 不放行；D2 未建立，D3 的“增益”没有基线；D4 没有同条件对照，不能解释环境影响；D6 没有对象和状态真值，不能做载荷识别。

### 4.10 当前项目建议的正式场景集合

为避免只采“容易目标”，正式数据应至少覆盖下列场景。场景名称是数据记录标签，不等于最终论文类别；无法可靠确认的对象使用 `other_target` 或“不确定”，不要强行归类。

| 场景组 | 建议标签 | 需要记录的变化 | 目的 |
|---|---|---|---|
| 背景组 | `background` | 开阔天空、建筑/树木、地面/金属反射、系统干扰、不同风况 | 估计虚警、近零多普勒结构和场地差异 |
| 现有方法延续组 | `uav` | 平台、飞行架次、距离/速度层、悬停/运动状态 | 与当前 H/V UAV 检测定位主线衔接 |
| 球体组 | `balloon_unloaded` | 球体规格、距离/高度、稳定/摆动状态 | 区分球体本身响应和载荷影响 |
| 有载组 | `balloon_loaded` | 载荷类别/质量/安装、绳长、状态起止 | 为有载/无载分层任务提供配对样本 |
| 非目标组 | `bird`、`other_target` 或“不确定” | 只有在视频/人工真值支持时才细分 | 测试检测前端对其他低空目标和干扰的区分 |

同一场地至少应有背景和一种目标；同一日期、配置和标定条件下优先完成一组目标/背景配对。若只能采到单一对象或单一天气，数据仍可用于接口和探索分析，但不能支持泛化结论。

### 4.11 每类实验的变量控制原则

为了让结果可以归因，每次实验只改变一个主要因素，并保留其余条件记录：

| 实验目的 | 主变量 | 应固定或配对的条件 |
|---|---|---|
| H/V 特征 | 通道输入/标定状态 | 雷达配置、距离、目标、场地、时间尽量固定 |
| 时域/时频特征 | 运动状态或连续慢时间窗口 | PRF、CPI、目标构型和观测时长固定 |
| 距离/速度定位 | 目标位置或运动速度 | 场地、配置、标定和目标构型固定 |
| 气象影响 | 风速/风向/阵风等 | 日期、场地、雷达配置、对象和真值方法记录完整 |
| 场地影响 | 开阔/建筑/树木等背景 | 同日期或相近时段采目标与背景，配置和标定一致 |
| 有载/无载 | 载荷构型 | 同一球体、绳长、距离、悬挂方式和运动状态尽量配对 |
| 实时性 | 输入流速、历史窗口和部署设备 | 模型 checkpoint、阈值、后处理和数据格式冻结 |

如果一次 session 同时改变多个主要因素，仍可作为探索数据，但不能用于支持某一个因素的因果结论。

## 五、第一轮 Pilot 的最小采集矩阵

这是用于“先证明采集链可用”的最低建议，不是最终论文样本量。每个 session 连续 2--5 分钟，全程视频和日志。

| 场景 | 目标状态 | 最低独立 session | 必须有的对照 |
|---|---|---:|---|
| S0 | 纯背景 | 3 | 同日期、同场地、同配置的目标缺失段 |
| S1 | 无载球 | 3 | 同日期/场地/配置的 S0 |
| S2 | 同一球体有载、稳定 | 3 | 同日期/场地/配置的 S0，尽量与 S1 配对 |
| S3 | 同一球体和载荷摆动或自然运动 | 3 | 同日期/场地/配置的 S0，记录状态起止 |

Pilot 还应包含：

1. 至少一次固定配置的连续写盘测试；
2. 至少 5 次雷达--视频--真值同步事件；
3. 现场读回 H/V、时长、序号、视频和文件大小；
4. 两份独立备份及哈希一致性检查。

Pilot 的重点是发现链路和标签问题，不是追求样本数量，也不能因为结果好看就改称 `locked_test`。

## 六、后续扩展采集建议

通过 Pilot 后，再扩展以下变化，每次只增加一类主要变量并保留对照：

| 变化维度 | 建议做法 | 主要目的 |
|---|---|---|
| 日期 | 至少覆盖多个独立日期 | 检查日期相关混杂和稳定性 |
| 场地 | 至少一个与 Pilot 不同的场地；条件允许时增加第二个 | 检查杂波和跨场地鲁棒性 |
| 气象 | 连续记录，按实际分布形成风/雨等分层 | 检查环境条件下的性能变化 |
| 对象 | 先固定 Pilot 对象，再增加载荷质量/外形/安装变化 | 区分对象差异与环境差异 |
| 状态 | 稳定、摆动、旋转或自然运动分别标记 | 为时域/时频特征提供可解释标签 |
| 距离/角度 | 在安全和设备能力允许范围内分层 | 检查定位误差和观测范围 |

具体样本数量应在设备能力、场地时间和导师意见确认后再冻结，不在尚未掌握设备吞吐和可用日期前虚构精确总样本量。

### 6.1 面向模型实验的采集矩阵

下表给出“数据到位后如何组成实验”的建议。每个格子至少应有多个独立 session；同一 session 切出的多个窗口仍属于同一个外层分组。

| 模型实验 | 训练/验证输入 | 必须的目标数据 | 必须的背景数据 | 关键分层 |
|---|---|---|---|---|
| Power2/RD 基线 | H/V 功率图、RD 或其明确派生形式 | UAV 和/或球体目标，带位置真值 | 同条件纯背景和非目标事件 | 距离、速度、SNR、日期、场地 |
| 时域/时频增量 | 连续慢时间 IQ、时域窗口、STFT 输入 | 有稳定、摆动或自然运动标签的目标 | 相同观测时长和配置的背景连续段 | PRF/CPI、运动状态、风况 |
| 极化增量 | Power2、复数 RD、相对 H/V 特征 | H/V 同步且标定状态明确的目标 | 同 session 或配对 session 的背景 | 通道有效性、标定 ID、功率水平 |
| ROI 精修 | 全图候选 + 候选附近局部窗口 | 目标位置和候选是否命中真值 | 背景峰、近零多普勒峰、困难虚警 | 候选距离/速度、原始分数、抑制后分数 |
| 环境/场地分层 | 任一冻结模型输入 | 每个条件下的目标事件 | 每个条件下的背景事件 | 日期、site、天气、SNR、对象 |
| 因果/实时回放 | 连续流和真实顺序 | 连续目标出现/消失事件 | 连续背景和干扰段 | 首帧、历史不足、丢帧、重启、队列 |
| 分层识别 | 检测前端输出 + 对象/状态特征 | `balloon_unloaded`、`balloon_loaded`、必要时其他目标 | 同条件背景和非球目标 | 对象实例、载荷、运动状态、场地 |

模型实验开始前，P2 数据负责人应生成一份分组清单，至少能回答：每个目标事件对应哪些背景对照、哪些窗口来自同一 session、哪些条件只存在于 development/validation、哪些数据保留给 locked test。

### 6.2 建议的最低连续记录长度

长度不是越长越好，关键是能覆盖完整事件和背景基线。以下是准备阶段建议值，最终以设备写盘实测和导师意见为准：

| 记录类型 | 建议长度 | 说明 |
|---|---:|---|
| 能力测试 | >= 300 s | 验证原始流稳定写盘和序号连续性 |
| Dry Run 纯背景 | >= 600 s | 覆盖启动、稳定、结束和异常恢复检查 |
| Pilot 单个 session | 120--300 s | 至少包含状态前段、目标状态和状态后段 |
| 正式目标事件 | 以完整出现--消失为准 | 不能只截取模型高分片段 |
| 正式背景段 | 与目标 session 同量级 | 支持事件级和时间归一化虚警统计 |
| 实时持续运行 | 建议 >= 600 s/配置 | 记录延迟分位数、丢帧、内存和队列变化 |

如果设备只能保存短窗口，必须同时给出窗口间隔、丢失时段和是否跨窗口连续；短窗口不能自动称为连续流。

### 6.3 必须保留的失败数据

以下数据不能因为模型表现差而删除：

- 同步失败、通道饱和、丢帧、时钟重置或写盘异常的 session；
- 目标操作偏离计划、视频不可见或真值不确定的 session；
- 模型漏检、误警、严重定位错误和极端天气样本；
- 被判定为 `REPEAT` 或 `REDESIGN` 的实验轮次。

失败 session 进入拒收/诊断清单，不进入性能主表；原始文件和原因仍要保留，以便导师和审稿人理解数据边界。

## 七、采集设备和人员准备

### 7.1 需要向设备方确认的仪器

- 双极化雷达及配置导出能力；
- 视频相机和统一时间源；
- GPS/RTK 或其他时间/位置参考；
- 测距、测角或全站仪等真值设备；
- 风速风向仪、温湿度/气压/降水传感器；
- 足够容量的本地存储、第二备份介质和供电；
- 安全防护、通信和场地许可。

若设备方不能提供某一项，应先记录“不可用”，再由导师决定是否收缩研究问题；不要事后用文件名或模型结果补写设备事实。

### 7.2 第一次外场建议人员

第一次建议由三名熟悉项目的成员组成小组，定位为设备学习、场地勘察和最小试采：

- 实验负责人：对外沟通、配置核对、异常记录和停止决定；
- 雷达操作/学习负责人：跟随设备方完成架设、启动、参数和导出记录；
- 真值与数据负责人：视频、目标状态、session log、现场读回和第二备份。

正式 Pilot 还必须明确目标操作、安全责任和备份责任。若合作方不提供雷达操作员，应增加成员或候补，避免一人同时操作雷达和目标。

## 八、数据目录和记录方式

每个 session 应形成一组互相引用的文件，而不是孤立的雷达文件：

```text
collection_root/
  raw_iq/ video/ truth/ radar_configs/ calibration/
  weather/ manifests/ session_logs/ hashes/
```

建议的 `session_id` 格式：

```text
YYYYMMDD_SITE_SCENARIO_RNN
```

原始 IQ、视频和真值首次落盘后只读；纠错通过新版 manifest 或派生标签完成，不覆盖原件。正式字段使用：

- [`data_collection_manifest_template_v1.csv`](../configs/data_collection_manifest_template_v1.csv)
- [`pilot_session_log_template_v1.csv`](../configs/pilot_session_log_template_v1.csv)
- [`field_sync_event_template_v1.csv`](../configs/field_sync_event_template_v1.csv)
- [`field_capability_response_template_v1.csv`](../configs/field_capability_response_template_v1.csv)

现场门禁和审计流程见 [`FIELD_COLLECTION_SOP_V1.md`](../docs/FIELD_COLLECTION_SOP_V1.md)；数据三档合同见 [`NEW_DATA_COLLECTION_PROTOCOL.md`](../docs/NEW_DATA_COLLECTION_PROTOCOL.md)。

## 九、放行与停止条件

| 检查项 | PASS 条件 | 未通过处理 |
|---|---|---|
| 设备能力 | H/V 内容、配置、扫描关系、连续写盘有证据 | `REPEAT` 或 `REDESIGN` |
| 时间同步 | UTC/硬件顺序明确，至少 5 次同步事件；Pilot 误差 P95 不超过 50 ms、最大不超过 100 ms | 修复后重做，不宣称 causal |
| 极化标定 | 通道映射、参考目标、相对幅相重复性和 `calibration_id` 可追溯 | 关闭相位类特征或重新标定 |
| 数据完整性 | 无未解释丢帧、饱和、缓存溢出；现场可读；双备份哈希一致 | 拒收 session，保留原件和诊断 |
| 对照设计 | 目标与背景同日期、场地、配置和标定条件可配对 | 重做对照，不做公平增益结论 |
| 标签真值 | 状态起止、位置和测量误差有记录 | 标记不确定或停止该任务 |
| 外层评价 | 模型、特征、阈值、后处理和指标冻结；锁定数据未参与开发 | 保持 `locked_test` 未执行 |

以下情况直接停止当前正式场景并保留诊断材料：H/V 缺失或映射不清、没有真实顺序、同步事件不可解释、文件无法读回、备份失败、目标超出安全边界，或只能靠删失败样本/改标签通过检查。

## 十、需要导师确认的事项

建议本文件提交导师后，优先确认以下问题：

1. 是否同意“E0 -> E1 -> E2 -> E3”的分轮采集路线；
2. 合作公司外场的雷达型号、操作人员、可用日期和场地权限由谁对接；
3. 是否能够获得 H/V 原始复数 IQ、真实时间/硬件序号和配置导出；
4. 定位真值采用哪些仪器，允许的距离/角度误差是多少；
5. 天气记录由项目组自带传感器还是使用场地/气象站数据；
6. 第一轮 Pilot 是否采用三人小组，目标操作和安全责任如何安排；
7. 是否同意先固定一个 Pilot 球体/载荷，再扩展对象和天气条件；
8. 本学期主线是否先聚焦检测与定位，把天气分类头、完整载荷分类和复杂物理反演列为后续方向；
9. 由哪位导师/学长作为采集合同、标签和锁定评价的验收人。

## 十一、会后交付物

导师确认后，项目组按以下顺序执行：

1. 完成设备能力确认单和外场权限确认；
2. 冻结第一版 `experiment_id`、`session_id`、manifest、session log 和同步事件表；
3. 完成 E0 连续写盘、同步和无球演练；
4. 通过 E0 后执行 E1 四场景 Pilot，并形成接受/拒收清单；
5. Pilot 通过后再确定 E2 的日期、场地、天气和对象扩展矩阵；
6. 所有模型结果绑定 manifest、split、配置、commit、checkpoint 和结果摘要；
7. 由导师/学长审阅后，才冻结 E3 的锁定评价方案。
